## 结论

**现在不要直接上压力测试。** P0 有 4 条，其中 3 条会在"多开 + 用另一个工作区的对话"这个具体场景下必然触发；第 4 条是安全链路（任意网页 → 本机任意命令），优先级高于所有稳定性问题。

最大的风险不是崩溃，是**"看起来卡死"**：注入脚本给每个副本挂了一条永不清理的 1.5s 定时器，里面做全量 DOM 几何 + 合成五连点击去驱动导航；一旦目标会话点不开（跨工作区、已归档、超出前 40 条），它就退化成"点别的行 → 页面重载 → 重新计数 → 再点"，9 个副本一起转，CPU 与日志同时失控，用户看到的是整块画布不响应。

架构层面的第二个硬伤：`proxyFor` 按**树序**分配端口（`client.js:3888-3907`），而 iframe 的 `src` 直接由它拼成（`client.js:1940`）。关一个窗、拖一下、插一张卡 → 下游所有窗口的 `src` 变了 → 全部重载。这与 commit `11a9c7a`「扁平绝对布局避免 iframe reload」的初衷正好相反。

## P0 阻断

### P0-1 `/frame` 反代无鉴权 + 无 host 白名单 + 代理覆盖会话 cookie ⇒ 任意网页可在本机执行任意命令

- **现象**：在浏览器卡片里打开任意站点 `https://evil.example/`，该页面的 JS 与内嵌的 DSH 副本**同源**（都在 `http://127.0.0.1:<代理口>`），可直接 `POST /_dsh/dsh-free-pane/exec` 让宿主起 PowerShell。不需要用户额外点授权。
- **位置**：
  - `index.js:496-503` —— `/frame` 在**任何鉴权之前**被代理层直接接管；
  - `index.js:389-402` —— 只校验 `/^https?:\/\//i`，不看 host，且 `fetch(target,{redirect:'follow'})`；
  - `index.js:516` —— `if (PROXY_COOKIE) headers.cookie = PROXY_COOKIE`，代理无条件用自己的合法 cookie 覆盖请求头；
  - `index.js:1663-1697` —— `ROUTES.exec` 直接 `execFileChild('powershell.exe', ['-Command', cmd], {cwd: args.cwd})`，无白名单、无审批；
  - `client.js:6996-7029` —— 终端卡就是这条 `/exec` 的正常入口，证明它不是"预留"接口。
- **根因**：为了绕开 `dsh-app://` 的跨站 cookie 问题，把"鉴权"和"取内容"两件事一起下放到了无鉴权的代理层，而代理又会**替请求补上**会话 cookie。于是 `/frame` 里的外部页面继承了一个"已登录"的同源上下文。
- **一句话修法**：给 `/frame` 加 host 白名单（`127.0.0.1`/`localhost` + 显式允许的域名）、禁掉 `redirect:'follow'`、并对 `/frame` 返回的页面下发 `Content-Security-Policy: sandbox` + 独立的无 cookie 代理口（或干脆只把 `/frame` 交给带鉴权的宿主路由）。

> 附带（同一条链上的小问题）：`index.js:408` 把上游整个 `arrayBuffer()` 读进内存，无大小上限、无超时、无 `AbortSignal`。拉一个 4GB 的 URL 就能把宿主进程内存打满——一个不需要恶意的"手滑"路径。

### P0-2 注入脚本的定时器永驻 + 每 tick 合成点击，目标会话点不开时退化成无限重载

- **现象**：开 3 个以上会话窗后整块画布变卡、鼠标拖动延迟、Task Manager 里渲染进程 CPU 长时间 100%；任务管理器之外的表现是"某个窗一直在转圈/一直在闪"。
- **位置**：
  - `index.js:1256-1258` —— `tick()` 立刻跑一次，然后 `setInterval(…,250)` 跑 80 次（前 20 秒 ×4Hz）后**新建** `setInterval(tick,1500)`，两个 interval 都**不清理**，随副本生命期常驻；
  - `index.js:896` —— 每 4 tick 一次 `plog("nav", …)`，且这次统计发生在"是否放弃"判断**之前**，于是放弃之后仍然 4 tick 一条日志；
  - `index.js:912` —— 每 tick `hardClick(row)`（`pointerdown→mousedown→pointerup→mouseup→click` 五连）；
  - `index.js:898` —— 放弃条件是 `tries++ > 400`，即最长 400 tick；
  - `tickBody` 每 tick 还会跑 `hideBodyLayers`（对 `body` 子节点逐个 `getBoundingClientRect`）、`hideDecor`、`hideRightColumn`（几何）、`trimRight`（`index.js:1230-1251`，从 `centerCol` 往上 3 层逐兄弟 `getBoundingClientRect` 再 `display:none`）。
- **根因**：把"一次性整容"做成了"永久巡检"，而且巡检里带**主动点击**。点击成功 → 页面导航 → 副本重载 → 副本内 `tries` 归零 → 再从 0 开始点。只要"点到了别的行"或"目标不可达"，这个环就是无限的，且**没有任何次数上限能跨 reload 生效**。
- **为什么压测会命中**：用户要用"**另一个工作区的对话**"。副本侧栏默认只展开当前工作区（`index.js` 的 `expandWorkspaces`/`pickWorkspace`），跨工作区的会话不在可见行里 → `openSession` 找不到目标 → 它继续在侧栏里点它**找得到的**行 → 导航到错误会话 → reload → 归零。这条路径是"跨工作区"这个测试场景的**默认**行为，不是边缘情况。
- **一句话修法**：把 tick 改成"有预算的收敛式"——`ok` 或超过 N 次（N≈60）就 `clearInterval` 彻底停；跨 reload 用 `sessionStorage` 记 `fpTries`，超过 3 次直接放弃并在窗内显示"这个会话需要你手动打开"；`plog` 加闸门。

### P0-3 一次渲染异常即写 `off=1` 永久停用，且恢复路径不清坏树

- **现象**：某张卡片渲染出一次异常，整个自由画布**永久消失**（刷新也不回来），右上角没有任何提示，只留一句"已经把插件自动关掉了"；点"重新启用"→ 再崩 → 再关，形成闭环。用户只能开 DevTools 删 `localStorage` 或用 `?fpReset=1` 才能脱身。
- **位置**：
  - `client.js:6769-6802` —— `CrashBoundary.componentDidCatch` 里 `localStorage.setItem('dsh-free-pane.off','1')`（`client.js:6783`）；
  - `client.js:7496-7499` —— 模块初始化时读这个键决定 `OFF_MODE`；
  - `client.js:6715-6730` —— `RecoveryCard` 的"重新启用"只 `removeItem(off)` + `location.reload()`，**不动 `TREE_KEY`**；
  - `client.js:6739-6743` —— `FreePaneTab` 分支**没有 `OFF_MODE` 判断**（主面板停了，右栏 tab 仍然会渲染画布，于是又能崩一次）。
- **根因**：把"降级"实现成了"全局自毁"，而"自毁原因"（持久化的坏树）恰好被保留下来。恢复路径不区分"偶发异常"与"确定性异常"。
- **为什么压测会命中**：压测会连着开十几种卡片（`client.js:4776-4800` 的 `?fpCards=1` 就是为此写的），任何一张新卡（尤其 `LiveGrab`，见 P1）抛一次，整套画布下线，且**下一轮压测仍然起不来**。
- **一句话修法**：`componentDidCatch` 不写 `off=1`，改为把出错的叶子替换成 `{kind:'empty'}`（或写 `off.until = now+60s` 的软降级）；`RecoveryCard` 加"重置布局（保留会话）"按钮，先 `TREE_KEY` 归一化再启用；`FreePaneTab` 也判 `OFF_MODE`。

### P0-4 `proxyFor` 按树序分配端口 ⇒ 任何一次增删拖拽都会让下游窗口整份重载

- **现象**：开了 4 个会话窗，随手关掉最左边那个，剩下 3 个**同时**开始重新加载（每个 20-30 秒），期间全部白屏；用户会认为"点一下把插件点崩了"。
- **位置**：
  - `client.js:3888-3907` —— `proxyFor(leafId)` 用 `treeEach` 数出该叶在"session/panel/browser 叶"里的**序号** `at`，再 `list[at % list.length]`；
  - `client.js:1940-1941` —— session iframe 的 `src` 直接拼 `api.proxyFor(leaf.id)`；
  - `client.js:1932-1944` —— 该 iframe **没有 `key`**，React 走属性 diff，`src` 一改就重新导航；
  - `client.js:3627` —— browser 卡同理，且 `key` 里还包含 `src`，等于双保险地重挂。
- **根因**：端口是"位置"的函数，而位置会变。设计文档（CHANGELOG 0.2.0）说"each session window takes one by tree order"，本意是"同一时刻两个窗不撞口"，但没考虑"位置变了要重新绑定"。
- **为什么算 P0 而不是 P1**：它命中的是最常见的操作（关窗、吸附、投放、换预设），且后果是"多个窗口同时白屏 20-30 秒"，用户会直接判定为卡死；更糟的是每个重载后的副本又重跑一遍 P0-2 的导航环。
- **一句话修法**：把 `proxyFor` 从"树序函数"改成"稳定租约"——用 `useRef({})` 存 `leafId → port`，只在端口表长度变化时重算，且重算时优先保留旧绑定；`live` 集合不变就保证 `src` 不变。

## P1 稳定性

### P1-1 父页面的三套"代劳"机制在跨源下 100% 是死代码

- `client.js:1463-1467`：`sweepFrame` 第一句 `var d = win && win.document` 包在 `try` 里，跨源必抛 `SecurityError` 被吞 → 后续 80 行（frame-probe 探针、禁用副本按钮、藏副本右栏）**永不执行**。
- `client.js:1581-1583`：`navFrame` 同样在取 `win.document` 时 `return`。
- 但 `client.js:1570-1571` 的注释明确写"两个副本同时挂载时副本里的定时器会静默停掉；父页面这边的定时器是活的，改由父页面代劳"——**这个论断在当前"每个副本一个 origin"的架构下不成立**：9 个端口 = 9 个 origin，父页面永远拿不到 `contentDocument`。
- 好的一面：`client.js:1560-1578` 的循环**逐帧 `try`**（1567、1572-1575），单帧抛异常不会中断后续帧，这一条（审计目标 4 里担心的"一次 sweep 某帧抛异常导致后面帧永远不处理"）是**已经正确隔离**的。
- 修法：删掉这两段（或改成 `postMessage` 下发指令给副本），别再维持一个永远不会跑的导航实现；注释同步改。

### P1-2 `liveCap` 一旦拿到小值就永不刷新

- `client.js:4434-4453`（`goProxy`）：只有成功拿到 `urls` 才 `setProxyList`，且**成功后不再刷新**；`client.js:3882-3886` 的容量又"只增不减"。
- 后果：宿主的 9 个代理口是**异步** listen 的（`index.js:1370-1375`），冷启动时 `/proxyUrl` 很可能只返回 2 个（`index.js:1738-1741` 会过滤假值）。客户端就把 `liveCap()` 永久钉在 2 —— 之后"全部挂起"（`client.js:3937-3948`）也拉不满，用户看到"最多并跑 2 份"，与 README:22 承诺的 9 个不符。
- 修法：`/proxyUrl` 一次性返回 9 个口（先 `listen` 完再响应，或让客户端在 `ports.length < 9` 时 3 秒后重试一次）。
- 已经做对的地方：`proxyCapRef` **只增不减**（`client.js:3879-3886`），避免了"端口表短暂变空 → 正在跑的副本被踢出活池 → iframe 卸载重挂 → 一直闪"。这个判断是对的，保留。

### P1-3 右栏治理每 700ms 做一次全画布强制同步布局

- `client.js:3952-4053`：`setInterval(…, 700)`，每 tick 都 `document.querySelector('[class*="rightbarCol"],…')`（3984 起从 `.fp-canvas` 往上 4 层遍历兄弟逐个 `getBoundingClientRect` 再 `hideNode`）、`querySelectorAll('[class*="_float_"],[class*="floatLayer"],[class*="FloatLayer"]')`；第 6 tick 还有一次 `document.body.querySelectorAll('div,aside,section')` 全量审计。
- 后果：与 P0-2 的 1.5s tick 叠加，主线程上每秒有 2-3 轮"读几何 → 写 `display` → 再读几何"的抖动，拖动分隔条时最明显（`moveDivider` 的 rAF 会被打断）。
- 修法：把这段挂到 `MutationObserver`/`ResizeObserver` 上，或至少降到 2s 且只在"右栏状态变化"时才跑；`hideNode` 前先看 `data-fp-hidden`（已有该模式）避免重复写。

### P1-4 `boundFor` 在渲染期做 O(N²) 全树摊平

- `client.js:4304-4353`：`boundFor(leaf)` 在 `treeEach` 里对**每个 session 节点**调一次 `geoRectOf(n.id)`；`client.js:4356-4366` 的 `geoRectOf` 每次 `querySelector('.fp-canvas')` + `getBoundingClientRect()` + **完整 `flatLayout` 摊平整棵树**再线性查找。
- 被 `client.js:1804/1952/2050/2085/3307/3483` 六处**每渲染**调用 → 一张 `usage`/`context` 卡的 `bindFor` = O(会话数) 次全树摊平 = O(N²) + 强制同步布局。
- 后果：`hover` 变化（`setHover`）会触发重渲染 → 6 张卡的 `bindFor` 全跑一遍。6 个会话窗时这是"每次鼠标划过接缝卡一下"。
- 修法：`flatLayout` 的结果每帧算一次存 ref，`geoRectOf` 只读缓存；`boundFor` 缓存到 `leaf.bindId`。

### P1-5 拖动标题栏会丢掉卡片内容（数据丢失）

- `client.js:5787-5812`（`endHeadDrag`）：构造的新内容只有 8 个字段 `{kind, sessionId, url, text, dir, cwd, tabKind}`。
- 丢的字段：`region` 的 `path`/`html`/`label`/`feed`、`browser` 的 `tabs`/`active`、`note` 的 `free`/`bindId`、`ocr` 的 `path`/`mode`/`stat`、`api` 的 `target`、以及 `zoom`/`minimized`。
- 后果：拖一次标题栏换个位置，那张卡片就变成"有壳没内容"（region 卡直接变空白、浏览器卡丢失全部标签页）。
- 修法：`endHeadDrag` 直接用整叶对象（`Object.assign({}, leafObj, {id: newId('w')})`），不要再手写字段白名单。

### P1-6 `resetDivider` 落盘的是旧树

- `client.js:5698-5703`：`setRoot(treeSetRatio(rootRef.current, id, 0.5))` 之后 `persist(rootRef.current)` —— `rootRef.current` 要等这次渲染后才更新，所以写回 `localStorage` 的是**改之前的树**。
- 后果：双击接缝还原 50%，刷新后回到旧比例。同类问题：`client.js:5252-5256` 的 `patch` 每次按键/每次 `pointermove` 都 `JSON.stringify` 整棵树写盘（`NoteLeaf` 里每敲一个字写一次）。
- 修法：`resetDivider` 里先 `var next = treeSetRatio(...)` 再 `setRoot(next); persist(next)`；`patch` 加 300ms 去抖。

### P1-7 自由拖拽没有 `pointercancel` 兜底

- `client.js:5714-5732` / `5734-5756`：`beginFreeDrag`/`beginFreeResize` 只监听 `pointerup` 收尾，没有 `pointercancel`、没有超时。对比 `beginDivider`（`client.js:5603-5607`）同时挂了 `pointercancel` + `window.blur` + **20000ms 兜底 `setTimeout`**——同一份代码里两种标准。
- 后果：触摸/笔/系统弹窗打断时，`document` 上的监听与 `fp-resizing` 类残留，画布进入"鼠标一动就改尺寸"的粘滞态。
- 修法：把 `beginDivider` 那套收尾逻辑抽成 `bindPointerSession(onMove, onUp)` 复用。

### P1-8 两个 `FreeCanvas` 实例共享同一个 `TREE_KEY`

- `client.js:5206-5208`（`persist`）、`client.js:6733-6743`（`FreePaneMain` 与 `FreePaneTab` 各自渲染一份）。
- 后果：主面板与右栏 tab 同时挂载时，两份实例各有 `root` state，谁写谁覆盖；`?fpMain=1` 探针（`client.js:7745-7760`）反复 `selectPanel` 时最容易出现"两个实例互相抢盘上的树"。
- 修法：`TREE_KEY` 加实例后缀，或用 `storage` 事件做单向同步（只让主面板写）。

### P1-9 `postMessage` 全程 `'*'`，接收端不校验 `origin`

- 发送：`client.js:607`（stats）、`client.js:6260-6280`（`bridgeTo`）、`index.js:434`（frame 的 navScript）。
- 接收：`client.js:3604-3619`（`BrowserCell.onNav`）、`client.js:5193-5196`（`fp-esc`）、`index.js` 的 message 处理段。
- 后果：浏览器卡里的任意页面都能 `parent.postMessage({fpNav:1,url:'…'},'*')` 让画布开新标签，或 `postMessage('fp-esc')` 反复收起面板。危害不大（不构成执行链），但属于"外站可以直接驱动宿主 UI"。
- 修法：发送端带上 nonce（已有 `FP_NONCE`），接收端比对 `FP_NONCE`；能确定 origin 时用具体 origin。

### P1-10 清单/入口不一致：底部工具条仍在提供两个"已知渲染不出"的面板卡

- `client.js:2748-2757`：`TOOL_BAR` 含 `panel:terminal`、`panel:files`。
- 而 `client.js:2225-2227` 的注释明说"官方面板卡片在副本里根本渲染不出来…与其挂个名字点了没反应，不如不列"，并用 `PANEL_CARDS_OK = false`（`client.js:2264`）门控了 EmptyPicker。
- 后果：点工具条上的"终端/文件"面板卡 → `canvasBody` 走 `panel` 分支（`client.js:2022-2056`）→ `wantKind` 有值但 `api.live` 里没有 → 显示"加载这个面板"→ 点下去建出的 iframe 在副本里渲染不出内容 → 用户看到空白窗。
- 修法：`TOOL_BAR` 里这两项改成本地 `terminal`/`files` 卡（`contentFor` 已支持，`client.js:5264-5304`）。

### P1-11 `LiveGrab` 的 `querySelector` 无 try，且首次 `grab()` 在 effect 里同步执行 ⇒ 非法选择器会把整块画布打掉

- `client.js:7085-7162`：effect 内 `for (…) { var cand = document.querySelector(sels[i]) }`（`client.js:7095-7096`）**没有 `try`**；而 `grab()` 在 `client.js:7158` 是**同步先跑一次**的，不是在定时器里。
- `sels` 的第 0 项来自 `client.js:1981` 的 `String(leaf.sel || '')`。只要某个 `feed:true` 的 region 叶子的 `sel` 是空串（旧版本持久化下来的树、或将来有人带 `feed` 造叶），`querySelector('')` 就抛 `SyntaxError`；因为抛在 effect flush 内，**React 会把它交给最近的 error boundary**，即 `CrashBoundary` → 走 P0-3 的 `off=1`，整块画布下线。
- 目前 `grabContent` 的 live 分支（`client.js:5316`）总会写非空 `sel`，所以这条是**潜伏/条件触发**，不是今天的必现路径；但它是 P0-3 唯一一条"能从外部数据触发"的入口，值得一起堵。
- 对比 `grabContent`（`client.js:5311`）是包了 `try` 的——同一份代码两种标准。
- 修法：`if (!sel) continue` + `try{ cand = document.querySelector(sel) }catch(e){ continue }`；`grab()` 整体再包一层 `try`。

### P1-12 日志无门控 + 宿主同步写盘 + 生产环境里的调试 dump

- `client.js:1068-1076`：`diag()` **无条件** `POST /_dsh/dsh-free-pane/log`（注释明确说"始终写日志，不受 fpTrace 门控"）；调用点还有 `client.js:2687`（每次片段点击）、`client.js:6343`（每次选类型）、`client.js:7151`（每次 LiveGrab）。
- 宿主侧 `index.js:1642-1651`：`fs.appendFileSync(%TEMP%\dsh-free-pane-trace.log)` —— **同步写、无上限、无轮转**。
- 注入脚本里还有两段**一次性结构 dump**：`index.js:879-885`（`__fpDump`，把前 10 个 `[data-row-key]` 的 key/展开态/文本写进日志）与 `index.js:888-895`（`__fpBtnDump`，`tries>44` 时把前 40 个按钮的 `aria-label`/`title`/文本/`className` 以及侧栏元素 `outerHTML` 的前 900 字符写进日志）。它们每个副本必跑一次，说明**导航逻辑到现在还是"带着探针上线"的状态**。
- 后果：压测 10 分钟，日志文件几十 MB，且每次写都在主线程同步落盘；日志里还留有用户界面的文本。
- 修法：`diag` 走 `trace` 的同一闸门（只有 `?fpTrace=` 才发）；把两段 dump 收进 `if(TRACE)`；宿主改成按大小轮转（>2MB 截断）或异步 append。
